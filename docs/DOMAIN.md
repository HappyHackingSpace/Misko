# Mişko — Domain Model (design)

> Status: design. Date: 2026-06-01.
> Scope: the data model Mişko owns as the **system of record**. The CV service
> (vision, raw telemetry, video) stays independent — see `docs/INTEGRATION.md`.
> Measurement architecture, metric definitions, MWM normalization and QC rules
> are specified in `docs/MEASUREMENTS.md`.

This document is the agreed target model before we touch `schema.prisma`. It
expands the current thin model (User, Device, Subject, Scenario, Test) into a
research-grade model that supports real behavioral-neuroscience workflows.

## 0. Tenancy & installation (single-tenant, on-prem)

Mişko is deployed **on-prem, one installation per laboratory**. There is exactly
**one `Laboratory`** per app — a singleton, not a multi-tenant system.

- **`Laboratory`** (singleton): `name`, `code`, `timezone`, `settings` (JSON),
  `createdAt`. Holds lab-wide configuration (settings, defaults).
- **Single-tenant simplification:** we do **not** sprinkle a `labId` foreign key
  across every table — everything implicitly belongs to the one lab. Multi-tenant
  is explicitly out of scope.
- **Installation wizard (CLI, at Docker startup):** a single bootstrap step takes
  the **lab name** + **superadmin email**, then creates the `Laboratory` **and**
  the `SUPERADMIN` user together (password generated by the system, printed once).
  A **singleton guard** refuses to create a second laboratory. Idempotent: if the
  lab already exists, it is a no-op. (Extends the existing `bootstrap-admin.js`.)

### 0.1 Environments (named instances of a paradigm)

The paradigm catalog is global and read-only (defined in code, see §1.1). A lab
turns a paradigm into one or more concrete, named, persisted **`Environment`**
instances (Turkish UI name: "Ortam"). A lab can hold **many** environments per
paradigm, e.g. two distinct Morris water tanks.

- **`Environment`**: `id`, `laboratoryId` (relation to `Laboratory`, onDelete
  Cascade), `name`, `paradigmKey`, `config` (JSON: a full self-contained snapshot
  `{ paradigmKey, schemaVersion, apparatus, zones }`), `notes?`, `createdAt`,
  `updatedAt`. Indexed on `laboratoryId` and `paradigmKey`.
- The environment's physical apparatus values are validated against the
  code-fixed parameter ranges at write time and are **locked at test time** (a
  test cannot override them).
- CRUD: `GET /api/environments`, `GET /api/environments/:id`,
  `POST /api/environments`, `PATCH /api/environments/:id` (`paradigmKey` is
  immutable on edit), `DELETE /api/environments/:id`. Writes require
  `apparatus:write` (RESEARCHER and above); reads only need auth.

## 1. Core idea: Paradigm ≠ Apparatus ≠ Calibration

The single biggest design decision. Three concepts that the old `Scenario`
conflated are split apart:

| Concept | Question it answers | Varies per | Owner |
|---|---|---|---|
| **Paradigm** | *What* is being tested & which metrics matter | fixed catalog | Mişko (seeded) |
| **Apparatus** | *Which physical rig* (geometry, color, size) | per lab/setup | Mişko |
| **Calibration** | *How camera pixels map to real-world cm + zones* | fixed rig or per session | Mişko (definition) / CV (homography) |

Why this matters for CV: the camera **does not infer** the paradigm or the
zones. The CV service detects and **tracks the animal** (centroid / bounding box
/ pose) frame by frame; the **geometry (zones in cm)** and the **pixel↔cm
mapping** are *provided* to it. A Test tells CV: `paradigm + apparatus +
calibration`. CV then projects the trajectory into the declared zones and
computes the metrics.

### 1.1 Paradigm — a hardcoded, SOLID code registry (NOT editable DB rows)

A paradigm is a **scientific test type defined in code**, not a row users edit.
This is deliberate: the *spec* (which parameters exist, which zones, which
metrics) is engineering-owned and stable; only the **values** are user data.

**Why code, not DB:** the same paradigm runs on physically different rigs — e.g.
the rotarod "stick" differs per lab (rod diameter, surface, fixed vs accelerating
speed). The paradigm declares *what is configurable*; the lab fills in the values
on an `Apparatus` (§1.2). One spec, many concrete rigs.

**SOLID shape** — each paradigm implements a common interface; the registry is
the single list. Adding a paradigm = adding a class, touching nothing else
(Open/Closed). The declarative `parameters` schema also lets the UI **auto-render
the settings form** and validate input (DRY).

```ts
interface ParadigmSpec {
  key: string;            // 'MWM' | 'OPEN_FIELD' | 'EPM' | 'ROTAROD' | ...
  name: string;
  category: string;       // learning_memory | anxiety | motor | social | ...
  parameters: Field[];    // {name, type, unit, default, min/max, options} → UI form
  zones(config): Zone[];  // derive concrete zones from the configured geometry
  metrics: MetricDef[];   // what the CV service must compute
  acceptance(config): Rule | null; // default pass/fail skeleton
  qc: QualityRequirement[]; // tracking, calibration, frame and lighting thresholds
  validate(config): void; // reject invalid parameter combinations
}

const PARADIGMS: Record<string, ParadigmSpec> = {
  MWM: new MwmSpec(),          // tank diameter, platform Ø, platform quadrant, water temp, opacity
  OPEN_FIELD: new OpenFieldSpec(), // arena W×L, center fraction
  EPM: new EpmSpec(),          // arm length/width, open/closed arms
  ROTAROD: new RotarodSpec(),  // rodDiameter_mm, surface, mode(fixed|accel), startRpm, endRpm, accel, maxDuration_s, laneCount
};
```

Initial registry (Phase target): `MWM`, `OPEN_FIELD`, `EPM`, `ROTAROD` (covers
the old POOL/MAZE/STICK/PATH intent); extensible by adding new specs.

> The paradigm catalog is **fixed in code** and read-only. A lab's concrete,
> named instances of a paradigm are data, modeled as `Environment` (§0.1).

The metric definitions are also fixed in code. `Test.result` is accepted only if
it matches the active paradigm's metric dictionary, result schema, QC
requirements and protocol version. Detailed rules live in
`docs/MEASUREMENTS.md`.

### 1.2 Apparatus (physical rig — the "environment")

The same paradigm can run on **different physical rigs**: a white tank vs a black
tank, different diameter, different platform position. CV accuracy depends on the
**animal-vs-background contrast**, so appearance is first-class here.

- `paradigmKey` (FK → Paradigm)
- `name` — e.g. "MWM tank — black, 120 cm"
- `shape` — `CIRCLE | RECT | PLUS | Y | CUSTOM`
- `dimensions` (JSON, cm) — e.g. circle: `{ diameter_cm: 120 }`; rect:
  `{ width_cm, length_cm, height_cm }`
- **`surfaceColor`** — e.g. `black | white | gray | other` *(CV: contrast)*
- **`material`** — e.g. `acrylic | pvc | painted_wood` *(CV: reflections/glare)*
- `paradigmConfig` (JSON) — paradigm-specific physical facts, e.g. MWM:
  `{ water_temp_c, platform_diameter_cm, platform_quadrant, water_opacity }`
- `zones` (JSON) — concrete zones for THIS rig, in **cm** relative to the
  apparatus origin (instantiates the paradigm's `zoneTemplate`). Each zone:
  `{ key, type, polygon_cm | circle_cm }`.
- `defaultCalibration` (FK → Calibration, optional) — used when the camera is
  fixed for this rig.

### 1.3 Calibration (camera ↔ world)

Supports **both** of the user's cases: a permanently mounted camera (calibrate
once, store on the apparatus) **and** a movable camera (calibrate per session,
override on the Test).

- `cameraId` — which camera/cage this calibration belongs to
- `referencePoints` (JSON) — pixel↔cm correspondences the operator marks on the
  camera image (e.g. 4 points on the tank rim)
- `homography` (JSON, 3×3) — derived pixel→cm transform
- `pxPerCm` (Float) — convenience scale
- `backgroundImageUrl` — reference frame (object storage URL; not the bytes)
- `createdAt`

Resolution order at test time: **Test.calibration** (per-session override) →
else **Apparatus.defaultCalibration** (fixed camera). If neither exists, the Test
can't be analyzed by CV until one is provided.

> Boundary note: the **zone/geometry definition (cm)** is experimental-design
> metadata → lives in Mişko. The **homography for a specific camera frame** is
> operational CV data; we store the definition/reference in Mişko so the setup is
> reproducible, while the CV service is free to recompute/refine it. To revisit
> together if we want to push homography fully to the CV side.

## 2. Subject (the mouse) — rich domain

The old `Subject` (code, sex, group, notes) is replaced by a research-grade
model. *(CV)* marks fields relevant to computer vision.

### Identity
- `code` (unique) — lab ID / cage label
- `microchipId` (optional) — RFID/transponder
- `earTag` (optional)

### Biological
- `species` — default `Mus musculus`
- `strain` — background strain, e.g. `C57BL/6J`, `BALB/c`
- `line` / `genotype` — transgenic line, e.g. `5xFAD`, `APP/PS1`, `WT`
- `zygosity` — `WT | HET | HOMO` (for transgenics)
- `sex` — `M | F`
- `birthDate` — age is derived, not stored
- **`coatColor`** — `black | agouti | albino_white | brown | other` *(CV: contrast vs apparatus surface)*

### Physiology
- **`weightLogs`** — time series, NOT a single field: `{ measuredAt, grams,
  notes }`. Many protocols weigh daily (food/water restriction, drug dosing).
- `healthStatus` / `notes`

### Housing & social
- `cageId`
- `litter` / `cohort`

### Lifecycle
- `status` — `ALIVE | SACRIFICED | DEAD`
- `acquiredAt`, `sacrificedAt` (optional)

### Experimental (relations, see §3 and §4)
- `diseaseModels[]` — N–N
- `treatments[]` — N–N (with dose/route/schedule)
- `groups[]` — membership in study groups

## 3. Disease models & treatments (both N–N)

A mouse can carry **multiple** disease models and **multiple** treatments at
once (confirmed requirement).

### DiseaseModel (catalog)
- `key` (unique), `name`, `category` — e.g. Alzheimer (`5xFAD`, `APP/PS1`),
  Parkinson (`MPTP`, `6-OHDA`, `alpha-syn`), Huntington (`R6/2`), stroke,
  depression models
- `description`

### SubjectDiseaseModel (join)
- `subjectId`, `diseaseModelId`
- `inducedAt` (optional), `method` (optional), `notes`

### Treatment (catalog)
- `key`/`name` — drug/compound or vehicle/control
- `defaultDose`, `unit`, `route` — `IP | ORAL | SC | IV | IN`, `notes`

### SubjectTreatment (join)
- `subjectId`, `treatmentId`
- `dose`, `unit`, `route`, `schedule` (JSON), `startedAt`, `endedAt`

## 4. Experimental design: Study → Group (longitudinal)

Confirmed: testing is **longitudinal** — the same mouse is tested repeatedly over
time, alongside other mice. Real labs organize around a Study with comparison
groups; this is what makes later statistics (control vs model vs treated)
possible.

### Study
- `title`, `hypothesis`, `startDate`, `endDate` (optional), `notes`

### Group (a.k.a. cohort/arm)
- `studyId` (FK), `name` — e.g. `control`, `model`, `treated_lowdose`
- `description`

### SubjectGroup (join, N–N)
- `subjectId`, `groupId`, `role` (optional)

### Longitudinal testing
- A `Test` references `studyId` (optional) and carries a `timepoint` label/index
  (e.g. `day_1`, `week_4`) so repeated runs of the same subject are comparable.

## 5. Test (the central transaction) — extended

Extends the existing `Test` to reference the new structure:

- `paradigmKey` (FK → Paradigm) — replaces the old free `scenario`
- `apparatusId` (FK → Apparatus)
- `subjectId` (FK → Subject)
- `operatorId` (FK → User)
- `deviceId` (FK → Device, optional)
- `studyId` (FK → Study, optional) + `timepoint` (optional)
- `calibrationId` (FK → Calibration, optional) — per-session override
- `status` — `PENDING | RUNNING | DONE | FAILED`
- `startedAt`, `endedAt`
- `cameraId` / `cageId` — boundary key for CV mapping
- `captureSessionId` (optional, unique) — set by CV on result push (idempotency)
- `result` (JSON) — CV summary metrics, shaped by the paradigm's `metricsSchema`
- `result.qc` (JSON object) — quality status and QC metrics such as tracking
  confidence, dropped frame ratio, calibration error, occlusion and lighting
  warnings. QC is separate from behavioral `passed`.
- `passed` (Boolean)
- `notes`

## 5b. Roles & permissions (RBAC)

The old `User.role` ("ADMIN" | "OPERATOR") is replaced by lab-oriented roles plus
a **code-defined permission matrix** (no DB-editable permissions — simpler, SOLID,
testable; changes ship with deploys).

### Roles (5)

| Role | Meaning |
|---|---|
| `SUPERADMIN` | The bootstrap user. Full control incl. user & lab configuration. |
| `LAB_MANAGER` | Runs the lab: manages users, configures the lab, full data access. |
| `RESEARCHER` | Designs studies, manages subjects/apparatuses, creates & runs tests. |
| `TECHNICIAN` | Executes tests, logs weights/measurements; limited subject edits. |
| `VIEWER` | Read-only across everything. |

### Permissions (resource:action)

`user:manage`, `lab:configure`, `study:write`,
`subject:write`, `weight:write`, `apparatus:write`, `test:write`, `test:run`,
and read access (`*:read`).

### Matrix

| Permission \ Role | SUPERADMIN | LAB_MANAGER | RESEARCHER | TECHNICIAN | VIEWER |
|---|:--:|:--:|:--:|:--:|:--:|
| `user:manage`     | ✅ | ✅ | — | — | — |
| `lab:configure`   | ✅ | ✅ | — | — | — |
| `study:write`     | ✅ | ✅ | ✅ | — | — |
| `subject:write`   | ✅ | ✅ | ✅ | — | — |
| `apparatus:write` | ✅ | ✅ | ✅ | — | — |
| `weight:write`    | ✅ | ✅ | ✅ | ✅ | — |
| `test:write`      | ✅ | ✅ | ✅ | — | — |
| `test:run`        | ✅ | ✅ | ✅ | ✅ | — |
| `*:read`          | ✅ | ✅ | ✅ | ✅ | ✅ |

### Enforcement

- The matrix lives in code (e.g. `config/permissions.js`): `ROLE → Set<permission>`.
- Middleware `requirePermission("test:run")` replaces ad-hoc `requireRole(...)`.
  `requireRole` stays usable for coarse checks, but permissions are the primary
  gate.
- `User.role` becomes an enum of the 5 roles; the bootstrap user is `SUPERADMIN`.

## 6. What stays out of Mişko (boundary recap)

- Per-frame trajectory/pose telemetry, event rows → **CV's PostgreSQL**.
- Video / trajectory files → **object storage**; Mişko stores only URLs
  (`backgroundImageUrl`, `result.artifacts.*`).
- No timeseries/telemetry table in Mişko (Timescale stays a CV-side option).

## 7. Entity map

```
Laboratory (singleton) ─< Environment (named instances of a paradigm)
        └─ User (role ∈ SUPERADMIN/LAB_MANAGER/RESEARCHER/TECHNICIAN/VIEWER)

Paradigm (code registry) ─┬─< Apparatus ──< Calibration (default, camera fixed)
          │        │
          │        └── zones (cm), surfaceColor, material, dimensions
          │
Study ─< Group ─< (N–N) Subject ─┬─< WeightLog
                                 ├─< (N–N) DiseaseModel  [SubjectDiseaseModel]
                                 └─< (N–N) Treatment     [SubjectTreatment]

Test = Paradigm + Apparatus + Subject + Operator + Device
        + Study? + timepoint? + Calibration? (per-session override)
        → result (CV metrics) + passed
```

## 8. Open points to revisit

1. Homography ownership — define-in-Mişko vs fully CV-side (see §1.3 note).
2. Whether `Group` membership should be time-bounded (mouse moves between groups).
3. Whether paradigm catalog becomes user-editable later (currently fixed).
4. Units policy: store everything in cm / seconds / grams, format in the UI.

## 9. Proposed implementation order (once approved)

0. **Foundation — tenancy + RBAC** *(new, do first)*
   - `Laboratory` singleton + installation wizard (extend `bootstrap-admin.js` to
     create lab + `SUPERADMIN` together; singleton guard).
   - 5-role enum + code permission matrix + `requirePermission` middleware;
     migrate existing ADMIN/OPERATOR users to the new roles.
1. **Paradigm registry + Environment** - code-defined, read-only `ParadigmSpec`
   registry (`MWM`, `OPEN_FIELD`, `EPM`, `ROTAROD`) + per-lab `Environment`
   instances created from a paradigm template.
2. **Subject domain** — rich Subject + `WeightLog` + `DiseaseModel`/`Treatment`
   catalogs + N–N joins. (User's top priority.)
3. **Apparatus** — geometry/zones/surfaceColor instantiating a paradigm's params
   (UI form auto-rendered from `parameters`).
4. **Calibration** — fixed (on apparatus) + per-session override on Test.
5. **Study/Group + longitudinal** — Test gets `studyId`/`timepoint`.
6. Migrations + seed updates + minimal UI (forms/lists) per step, each gated by
   the relevant permission.
